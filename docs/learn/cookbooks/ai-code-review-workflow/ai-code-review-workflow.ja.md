# Fabric でコードレビューのワークフローを実行する

**所要時間:** セットアップ10分、その後継続利用  
**難易度:** 初級  
**作成するもの:** Fabric の `/review` コマンドと差分ビューアを使った、繰り返し利用できるコードレビューのワークフロー。

---

## 概要

Fabric の `/review` コマンドは、プロジェクト内の任意のファイルに対して、6つの観点 — 正確性、セキュリティ、パフォーマンス、保守性、テスト、ベストプラクティス — から構造化された分析を実行します。重大度の評価と具体的な提案を含む、優先順位付けされたレポートを返します。

レビューを得たら、Fabric に修正を適用するよう依頼し、何かをコミットする前に、インタラクティブな差分ビューアで各変更を確認できます。

このクックブックでは、サイクル全体を通して説明します。レビュー → 指摘事項の確認 → 修正の適用 → 検証。

---

## ステップ1: レビューしたいファイルを開く

ファイルブラウザで、レビューしたいファイルに移動します。クリックしてエディタで開き、右クリックして **Add to Chat** を選択し、コンテキストとして添付します。

あるいは、このステップを省略することもできます — `/review` コマンドは、ファイルパスを引数として直接受け取れます。

---

## ステップ2: レビューを実行する

チャット入力欄に、次のように入力します。

```
/review src/auth/token.ts
```

パスをあなたのファイルに置き換えてください。Fabric はファイルを読み込み、分析し、構造化されたレポートをストリーミングで返します。

レポートは指摘事項を重大度別に整理します。

- **Critical** — バグ、セキュリティ脆弱性、データ損失のリスク
- **Major** — ロジックエラー、パフォーマンスの問題、エラー処理の欠如
- **Minor** — スタイルの問題、命名、DRY 違反

各指摘事項には、正確な行または関数、問題の説明、推奨される修正が含まれます。

---

## ステップ3: レポートを注意深く読む

すぐに Fabric にすべてを修正させようとしないでください。指摘事項を読み通し、次のように判断します。

- 確実に実在する問題で、修正したいものはどれか
- 自分が同意しないスタイル上の好みはどれか
- この変更の範囲を超えたリファクタリングが必要になるものはどれか

PR レビューでは、Critical と Major の指摘事項に注目しましょう。Minor の問題は修正する価値はありますが、マージをブロックすべきではありません。

---

## ステップ4: Fabric に特定の修正を適用するよう依頼する

「すべて修正して」ではなく、選択的に依頼します。

```
validateToken() のトークン有効期限チェックの欠落に対する修正を適用して。
それ以外はすべてそのままにして。
```

Fabric は編集ツールを使って対象を絞った変更を行い、その結果を差分ビューアで表示します。

---

## ステップ5: 差分を確認する

差分ビューアは、左に元のコード、右に提案された変更を表示します。各変更について:

- `A` を押すと、ハイライトされた変更を**承認**します
- `D` を押すと、それを**破棄**します
- `W` / `S` を使って変更間をスクロールします
- ファイル単位のコントロールを使って、すべての変更を一度に承認または却下します

ここでは時間をかけてください。あなたはコードが変更される前の最後の防衛線です。

---

## ステップ6: 反復する

修正を適用したら、同じファイルに対して再度レビューを実行します。

```
/review src/auth/token.ts
```

2回目のレビューがクリーンなら、問題は解決されています。新しい指摘事項が現れた場合、それはおそらく修正によって持ち込まれたものです — 次に進む前に、ざっと確認する価値があります。

---

## ステップ7: テストを実行する

組み込みターミナルで:

```bash
npx vitest run src/auth/token.test.ts
```

コミットする前に、変更したファイルのテストは必ず実行しましょう。このファイルのテストがない場合は、Fabric に書いてもらいましょう。

```
validateToken() のユニットテストを書いて。正常系、有効期限切れのトークン、不正な入力をカバーすること。
```

---

## バリエーション

**PR の後ではなく前にレビューする** — 問題を疑ったときだけでなく、PR を開く前に、変更したすべてのファイルに対して `/review` を実行しましょう。コードをじっと見続けていると見落としがちなことを捉えてくれます。

**他人のコードをレビューする** — ファイルブラウザからファイルを開き、`/review` を実行します。不慣れなモジュールを理解したり、同僚の PR を監査したりするのに役立ちます。

**レビューを絞り込む** — 完全な分析の代わりに、絞り込んだレビューを依頼することもできます。

```
src/payments/stripe.ts をセキュリティの問題のみについてレビューして。
```

**学習に使う** — コードベースや言語に不慣れな場合、自分が書いたファイルに対する `/review` は、自分のコードについて具体的で実行可能なフィードバックをすばやく得る方法です。

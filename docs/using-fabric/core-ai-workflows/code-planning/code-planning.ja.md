# Fabric によるコードプランニング

## Fabric によるコードプランニングとは？

コードを一行も書く前に、Fabric は機能や変更に対する包括的なエンジニアリングの設計図を作成できます。実際のコードベースをスキャンし、そのパターンを理解したうえで、アーキテクチャからテスト戦略まですべてを網羅した構造化された計画を提供します。

コードプランニングは、汎用的なアウトライン生成ツールではありません。Fabric はリクエストに関連するファイルを読み込み、コードベースが現在どのように構成されているか（ストア、サービス、UI パターン、データフロー）を分析し、**プロジェクトに固有の**計画を作成します。その結果として得られるのは、`/implement` に直接引き渡したり、並列のサブエージェントに委任したりできる詳細なドキュメントです。

### 計画に含まれる内容

一般的な計画には、次の項目が含まれます。

| セクション | 内容 |
| :--- | :--- |
| **概要と目標** | 機能とその受け入れ基準の正確な再記述 |
| **コードベース調査の要約** | Fabric がファイルを読み込んで発見した内容 — 既存のパターン、関連するストア、潜在的な競合 |
| **提案されたアーキテクチャ** | 新しいコードの配置場所、その依存先、およびその理由 |
| **ファイルレベルの変更** | 作成または変更するファイルの順序付きリストと、各変更の説明 |
| **実装シーケンス** | 依存関係を尊重し、リグレッションを回避するための段階的な順序付け |
| **テスト戦略** | 特定のコードパスに紐づいたユニット、統合、E2E テストの推奨事項 |
| **リスクと緩和策** | 既知の落とし穴、エッジケース、およびそれらへの対処方法 |
| **SOLID 原則のチェック** | 提案された設計が SOLID 原則をどのように支持または問題提起するかの分析 |

## プランニングプロセスの仕組み

### ステップ 1 — 構築したいものを記述する

チャットタブを開き、機能を平易な言葉で記述します。特別なコマンドやスラッシュ構文を使う必要はありません。自然に書くだけです。Fabric はあなたのメッセージと、ワークスペースで開いているファイルを併せて使用し、必要な完全なコンテキストを収集します。

**目標と制約**について具体的であるほど、計画はより的確になります。例えば次のようになります。

> *「ユーザー設定管理機能を追加するための詳細な実装計画を作成してください。通知設定、テーマ設定、設定可能なキーボードショートカットを網羅する必要があります。」*

![プランニングのリクエストをチャット入力欄に入力する](../../../assets/screenshots/code-planning/1.png)

### ステップ 2 — Fabric がコードベースを調査して計画を立てる

送信後、Fabric はすぐに汎用的な計画を生成するわけではありません。代わりに、計画を一文字も書く前に**能動的な調査**を実行します。

* 関連するファイルを読み込みます — 例えば、既存の設定画面、ストアスキーマ、IPC ハンドラー、関連する UI コンポーネントなどです。
* ターゲットを絞った検索（`grep`、ファイル読み込み）を実行し、現在の実装状況を理解します。
* すでに存在するものと、構築する必要があるものを論理的に推論します。
* 全体像が明確になると、調査結果をチャットで要約し、その後に完全で構造化された計画を作成します。

このプロセスはチャットでライブで確認できます。各ツール呼び出し（ファイル読み込み、grep など）がインラインで表示され、Fabric が何を検証しているかを完全に透明な形で把握できます。

![Fabric が計画を作成する前にコードベースのファイルを能動的に読み込む](../../../assets/screenshots/code-planning/2.png)

## 計画が生成された後

計画がチャットに表示されたら、いくつかの選択肢があります。

* **対話的に改良する** — フォローアップの質問をして任意のセクションを拡張したり、代替アプローチを要求したり、スコープを調整したりできます。Fabric は計画をその場で更新します。
* **`/implement` に引き渡す** — 計画を Markdown ファイルに保存し、その URL を `/implement` スラッシュコマンドに渡して、分離された Git ワークツリー内で実行します。
* **サブエージェントに委任する** — 計画をタスク分解として使用し、並列のサブエージェントを（`/implement_with_dag` 経由で）生成して、異なるセクションを同時に作業させます。
* **レビューのチェックポイントとして使用する** — コードを書く前にチームと計画を共有し、アーキテクチャ上の問題を早期に発見します。

> [!TIP]
> プランニングのリクエストを送信する前に、機能に最も関連するファイルをエディタタブで開いておきましょう。Fabric はワークスペースのコンテキストを使用します。関連するファイルが多く表示されているほど、計画はより的確になります。

> [!NOTE]
> コードプランニングは、強力な推論能力を持つモデルで最も効果を発揮します。複雑で複数ファイルにまたがるプランニングのリクエストには、**Fabric XLarge** をお勧めします。
